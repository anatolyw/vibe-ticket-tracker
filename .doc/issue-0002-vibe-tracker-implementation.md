> **Status:** Planned

## General Description

**Vibe Ticket Tracker** is a self-contained, locally-hosted ticket tracking system designed for "vibe coders" — developers (or AI agents) who work on small to medium projects and need to track every change as part of living project documentation.

The system consists of two main parts:

1. **The `vibe-tracker` npm package** — A CLI tool and web application that runs on `localhost` with no external dependencies. It provides:
   - A CLI with `init` (project setup) and `start` (launch server) commands.
   - An Express.js API for ticket CRUD operations.
   - MCP endpoints (tools + resources) so AI agents can create, read, update, list, and delete tickets programmatically.
   - An Angular SPA UI with a responsive sidebar, dark/light theme, search/filter/sort, and a markdown editor with live preview.
   - Tickets are stored as plain `.md` files with YAML frontmatter in a `.vibe-tracker/` directory inside the project — human-readable, version-controlled, and AI-friendly.

2. **An example demo project** (`vibe-tracker-example-project/`) — A reference project that uses `vibe-ticket-tracker` via `npm link`. It includes:
   - A generated `vibe-ticket-tracker.json` config.
   - An `opencode.jsonc` file pointing OpenCode's MCP client to the vibe-ticket-tracker server.
   - A `VIBE-TRACKER-SKILL.md` agent skill file that codifies the rules for how AI agents should use the tracker during development (create tickets before work, branch per ticket, prefix commits, one ticket per session, no merge without instruction, etc.).

### Workflow

The intended usage is straightforward:

1. **Install** the package into a project (`npm link` during dev, `npm install` after publishing).
2. **Initialize** with `vibe-ticket-tracker init` — creates config, ticket directory, and helper scripts.
3. **Start** with `vibe-ticket-tracker start` — builds the Angular UI, serves it as a SPA, exposes the REST API and MCP endpoints on a single port.
4. **Develop** — the developer (or AI agent) creates tickets before any code changes, works on them, tracks progress, and closes tickets when done. The project's git history provides the audit trail.

### Key Design Decisions

- **Ticket files** are Markdown with YAML frontmatter — the best balance between human readability and machine parseability.
- **Ticket type** (`issue`/`feat`/`bug`) lives in frontmatter, not in the filename. The filename uses only the configured prefix (e.g., `issue-00001-title-suffix.md`).
- **Theme** (dark/light) is user-preference only, persisted in `localStorage`.
- **No concurrency** — single-seat assumption. Simple overwrite on save.
- **No attachments** — pure text only.
- **No internal versioning** — the project's git history is the source of truth for change history.
- **Angular standalone + signals** — no NgModules, pure modern Angular patterns.
- **Responsive design** — sidebar adapts from hamburger overlay (small screens) to icon-only (medium) to icon+text with collapse toggle (large).

## 2. Vibe Ticket Tracker App Package

### 2.1 CLI (`bin/vibe-ticket-tracker`)

Two commands:

| Command | What it does |
|---|---|
| `vibe-ticket-tracker init` | Creates `vibe-ticket-tracker.json` in CWD, creates `.vibe-tracker/` directory, adds npm scripts to project `package.json` |
| `vibe-ticket-tracker start` | Reads `vibe-ticket-tracker.json`, resolves port + doc root, builds Angular UI (if not built), starts Express server |

CLI uses `commander` for argument parsing.

### 2.2 Config (`vibe-ticket-tracker.json`)

```json
{
  "VIBE_TRACKER_PORT": 61000,
  "VIBE_TRACKER_DOC_ROOT": ".vibe-tracker",
  "VIBE_TRACKER_TICKET_PREFIX": "issue",
  "VIBE_TRACKER_TICKET_TYPE_OPTIONS": ["issue", "feat", "bug"],
  "VIBE_TRACKER_TICKET_NUM_PATTERN": "XXXXX",
  "VIBE_TRACKER_TICKET_SUFFIX_LENGTH": 80
}
```

- **`VIBE_TRACKER_PORT`**: Running port — default `61000` (above 60000 as specified).
- **`VIBE_TRACKER_DOC_ROOT`**: Root directory for ticket documents. Default: `.vibe-tracker`.
- **`VIBE_TRACKER_TICKET_PREFIX`**: Filename prefix. Example: `issue`.
- **`VIBE_TRACKER_TICKET_TYPE_OPTIONS`**: Array of allowed ticket types. Default: `["issue", "feat", "bug"]`. The type is stored *inside* the ticket frontmatter (not in the filename). The dashboard/tickets page shows a type filter.
- **`VIBE_TRACKER_TICKET_NUM_PATTERN`**: Number pattern. `XXXXX` means 5 digits, range 00001–99999.
- **`VIBE_TRACKER_TICKET_SUFFIX_LENGTH`**: Maximum character length of the title-derived suffix in the filename. Default: `80`.

### 2.3 Ticket File Format

#### Filename

Format: `{prefix}-{NNNNN}-{suffix}.md`

- Example: `issue-00001-add-login-page-with-oidc-auth.md`
- Suffix is generated from the ticket title: lowercase, spaces → hyphens, strip special chars, truncated to `VIBE_TRACKER_TICKET_SUFFIX_LENGTH`.

#### Frontmatter (YAML)

```yaml
---
id: "issue-00001"
title: "Add login page with OIDC auth"
type: "issue"
status: "open"
created: "2025-01-15T10:30:00Z"
updated: "2025-01-15T10:30:00Z"
---
```

#### Body (Markdown)

```markdown
# Add login page with OIDC auth

## Description
Implement login page supporting OIDC flow...

## Tasks
- [ ] Set up auth service
- [ ] Create login component
- [ ] Add OIDC callback route
- [ ] Write unit tests

## Notes
- ...

## Changes
### Files modified
- `src/app/auth/login.component.ts`
- `src/app/auth/auth.service.ts`

### Code changes summary
- Added login form with email/password
- ...
```

> See [Section 5](#5-yaml-validation-schema-for-ticket-frontmatter) for the full validation schema.

#### Key Design Decisions

- **Markdown rendering in UI**: Ticket detail view renders markdown as formatted HTML by default. An "Edit" button switches to the raw markdown view. "Save" commits the changes and returns to rendered view.
- **Ticket type**: Stored in YAML frontmatter as `type` (e.g., `issue`, `feat`, `bug`). Not part of the filename — the filename uses only the `VIBE_TRACKER_TICKET_PREFIX`.
- **Attachments**: Pure text only. No file/image attachments.
- **Versioning**: Simple overwrite on save. Version history is tracked via the project's git history, not internal audit trails.
- **Concurrency**: No file locking or concurrency handling — single-seat vibe coding assumption.

### 2.4 Express Server

#### REST API Endpoints

| Method | Path | Description |
|---|---|---|
| `GET` | `/api/tickets` | List all tickets (query: `?status=open\|closed`, `?type=issue\|feat\|bug`, `?prefix=issue`, `?search=term`, `?sort=created\|updated\|title`, `?order=asc\|desc`, `?limit=20`, `?offset=0`) |
| `GET` | `/api/tickets/:id` | Get a single ticket by ID (returns structured JSON with frontmatter + body) |
| `POST` | `/api/tickets` | Create a new ticket (body: `{ title, type, description? }`; validates against frontmatter schema) |
| `PUT` | `/api/tickets/:id` | Update a ticket (body: partial or full; validates against frontmatter schema) |
| `DELETE` | `/api/tickets/:id` | Delete a ticket file |
| `GET` | `/api/tickets/:id/raw` | Get raw markdown content (for MCP resource access) |

#### Static File Serving

Angular build output is served from `dist/ui/` at the root `/`.

#### Server Startup Flow

```
vibe-ticket-tracker start
  → read vibe-ticket-tracker.json
  → resolve port (default 61000)
  → resolve doc root (default .vibe-tracker)
  → build Angular to dist/ui/ (skip if dist is newer than src)
  → Express serves:
      GET /         → Angular static SPA
      GET /api/*    → Ticket REST API
      GET /mcp      → MCP JSON-RPC endpoint
```

### 2.5 MCP — Tools + Resources

#### MCP Tools (structured operations for AI agents)

| Tool Name | Description | Parameters |
|---|---|---|
| `vibe_tracker_create_ticket` | Create a new ticket | `title` (string, required), `type` (string, required, from prefix config), `description` (string, optional) |
| `vibe_tracker_update_ticket` | Update an existing ticket | `ticket_id` (string, required), `fields` (object, optional — partial: `title`, `type`, `status`, `description`) |
| `vibe_tracker_delete_ticket` | Delete a ticket | `ticket_id` (string, required) |
| `vibe_tracker_list_tickets` | List tickets with filters | `status` (string, optional), `type` (string, optional), `prefix` (string, optional), `limit` (number, optional, default 50), `offset` (number, optional, default 0), `sort_by` (string, optional), `sort_order` (string, optional) |
| `vibe_tracker_get_ticket` | Get a single ticket | `ticket_id` (string, required) |

#### MCP Resources (file-based access for AI agents)

| Resource URI Pattern | Description |
|---|---|
| `vibe://tickets/{id}` | Full ticket content as rendered markdown |
| `vibe://tickets/{id}/raw` | Raw markdown source |
| `vibe://tickets/{id}/metadata` | Ticket metadata as JSON (frontmatter only) |
| `vibe://tickets/` | Index of all tickets (JSON array of summary objects) |
| `vibe://config` | Current vibe-tracker configuration |

#### 2.6.3 UI Features

##### Dashboard (`/`)

- **Stats cards**: total tickets, open, closed. Each card shows count with trend indicator.
- **Breakdown by type**: row showing issue/feat/bug counts.
- **Recent tickets**: last 5-10 tickets sorted by updated date.
- **Quick-create**: button linking to `/tickets/new`.

##### Ticket List (`/tickets`)

- **Search**: full-text search across ticket title and body description.
- **Filter — Type**: dropdown with all configured types (issue, feat, bug) + "All".
- **Filter — Status**: dropdown with "All", "Open", "Closed".
- **Sort**: selector for `created date`, `updated date`, `title` — each with asc/desc toggle.
- **Pagination**: page-size selector (10/25/50), page number navigation.

##### Ticket Detail (`/tickets/:id`)

- **Rendered mode** (default):
  - Renders markdown as formatted HTML using `@tailwindcss/typography` (`prose` class).
  - Shows metadata badges: type (colored), status (colored), created, updated.
  - "Edit" button switches to edit mode.
- **Edit mode**:
  - Shows the raw markdown in a `<textarea>` (including YAML frontmatter).
  - "Save" validates against the frontmatter JSON schema, persists the file, and switches back to rendered mode.
  - "Cancel" discards changes and returns to rendered mode.
- **Actions**:
  - Status toggle: button to switch between `open` and `closed`.
  - Delete: confirmation dialog, then navigates back to list.

##### Theme Toggle

- Sun/moon icon button in the header.
- Toggles `dark` class on `<html>` element.
- Persisted in `localStorage` as `vibe-tracker-theme`.
- Respects `prefers-color-scheme` on first visit (no stored preference).
- Implemented via Tailwind CSS `dark:` variant + Angular class binding.

#### 2.6.4 Responsive Design

| Breakpoint | Width | Sidebar Behavior |
|---|---|---|
| **Small** | `< 768px` | Sidebar hidden. Hamburger button (top-left of header) toggles overlay sidebar with semi-transparent backdrop. |
| **Medium** | `768px – 1023px` | Collapsed sidebar, always visible. **Icons only** (no text). |
| **Large** | `≥ 1024px` | Expanded sidebar, always visible. **Icon + text**. Collapse/expand toggle button visible. |

##### Collapse Toggle (Large Screens Only)

- Double-arrow icon button in the sidebar header.
- When collapsed: sidebar shrinks to icon-only mode (same visual as medium).
- Text label: "Collapse sidebar" (visually hidden via screen-reader-only class when collapsed, shown when expanded).
- Collapse state persisted in `localStorage` as `vibe-tracker-sidebar-collapsed`.
- **Hidden on medium screens** — no toggle needed since medium always shows icons.

##### Small Screen Sidebar (Overlay)

- Slides in from the left when hamburger is tapped.
- Semi-transparent backdrop (click to close).
- Closes on: hamburger tap, route navigation, backdrop tap.
- Full-width or ~300px wide (whichever is smaller).

### 3.3 `VIBE-TRACKER-SKILL.md` — Agent Rules

```markdown
# Vibe Ticket Tracker Skill — Agent Rules

## Core Principles
You are a vibe coder assistant. Before writing any code, you MUST use the
vibe-ticket-tracker to create and manage tickets. Every change must be tracked.

## Ticket Workflow

### 1. Create a Ticket Before Starting Work
- Use `vibe_tracker_create_ticket` via MCP before any code changes.
- Include a detailed plan in the ticket description.
- Outline ALL changed files the ticket will touch.
- Include acceptance criteria.

### 2. Naming Conventions
- Ticket titles should be concise but descriptive.
- Prefix with the action: `add`, `fix`, `refactor`, `remove`, `update`.
- Example: `add login page with OIDC auth`

### 3. File Change Outline
Every ticket MUST include a "Files modified" section listing every file
that will be created or changed.

### 4. Git Branching
- When starting work on a ticket, create a new git branch:
  `git checkout -b issue-00001-add-login-page`
- The branch name must match the ticket ID and a short description.

### 5. Commit Messages
- All commits MUST be prefixed with the ticket ID:
  `issue-00001 add login component and auth service`
- Use conventional commit style after the prefix.

### 6. One Ticket Per Session
- Work on exactly one ticket per session.
- If you notice potential work that could be a separate topic, suggest
  creating a new ticket and starting a fresh session for it.

### 7. No Merging Without Explicit Instruction
- Never merge your branch to main/trunk.
- Wait for explicit `merge` or `finish` instruction from the user.

### 8. Update Ticket Status
- Set ticket to `open` when created.
- Set ticket to `closed` when all tasks are complete.
- Include a "Changes" section in the ticket when closing:
  - List of files modified
  - Summary of code changes
  - How acceptance criteria were met

### 9. Read Existing Tickets First
- Before creating a new ticket, check if a similar one already exists.
- Reference related tickets in the new ticket's description.

### 10. Keep Tickets Living Documents
- Update tickets as you work — add notes, mark tasks complete.
- Don't just create and forget. The ticket IS the project documentation.

## Ticket Type Usage

Choose the correct ticket type when creating:

| Type | When to use |
|---|---|
| `issue` | General problems, bugs, missing features, or any task that doesn't fit feat/bug |
| `feat` | New features, enhancements, or additions to existing functionality |
| `bug` | Fixing an existing bug or regression in the codebase |

## Acceptance Criteria Checklist

Every ticket must include:
- [ ] Description of what needs to be done
- [ ] List of files to be created/modified
- [ ] Step-by-step plan or tasks
- [ ] Acceptance criteria (how do we know it's done)

## When Closing a Ticket

Before marking a ticket as closed, verify:
- [ ] All tasks are complete
- [ ] Code follows project conventions
- [ ] Changes section is complete with file list and summary
- [ ] Branch is ready (not merged yet, awaiting user instruction)

## Vibe Ticket Tracker UI Best Practices

- Use the dashboard to see the overall project state at a glance.
- Filter and sort tickets in the list view to find relevant work quickly.
- When editing a ticket via the UI, always update the frontmatter metadata.
- Use the search bar to find tickets by keyword across title and description.
- The theme toggle (dark/light) is user-preference only — do not change it programmatically.
- Type badges (issue/feat/bug) help visualize the nature of work in the project.
```

## 4. Additional Details

### 4.1 Ticket Numbering

- Auto-increment based on existing tickets in `.vibe-tracker/`.
- The next available number is derived from the highest numbered ticket + 1.
- Pattern `XXXXX` allows 00001–99999 (5 digits).
- If all numbers are taken → clear error message.

### 4.2 File Name Suffix

- Generated from ticket title: lowercase, spaces → hyphens, remove non-alphanumeric/hyphen characters, collapse multiple hyphens.
- Truncated to `VIBE_TRACKER_TICKET_SUFFIX_LENGTH` characters.
- Example: `"Add login page with OIDC auth"` → suffix: `"add-login-page-with-oidc-auth"`
- Full filename: `issue-00001-add-login-page-with-oidc-auth.md`

### 4.3 Error Handling

| Scenario | Behavior |
|---|---|
| Missing `vibe-ticket-tracker.json` | CLI prompts for config values interactively |
| Invalid port number | Falls back to default (61000) |
| Duplicate file name (suffix collision) | Appends `-1`, `-2`, etc. |
| Disk full / permission errors | Clear error message to CLI output |
| Invalid YAML in ticket frontmatter (edit save) | Shows validation error, prevents save, highlights invalid fields |
| Ticket ID not found | 404 JSON error response + UI toast notification |

### 4.4 Angular Build Integration

- Angular builds to `dist/ui/` within the `vibe-tracker/` package during `start`.
- If Angular source has not changed since last build, skip rebuild (check timestamps).
- No NgModules — pure standalone components throughout.
- `provideHttpClient()` for API communication.
- `provideRouter()` for routing.

## 5. YAML Validation Schema for Ticket Frontmatter

Based on the compaction schema pattern from `compaction-schema.json`, this JSON Schema validates the YAML frontmatter in ticket markdown files. It is used by:

- The **API** (`POST /api/tickets`, `PUT /api/tickets/:id`) to reject invalid payloads.
- The **UI editor** to prevent saving tickets with missing required fields or invalid values.
- The **CLI** to validate new ticket creation.

### 5.1 Schema File

**Path**: `vibe-tracker/src/server/storage/ticket-schema.json`

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://vibe-tracker.local/schema/ticket-frontmatter.json",
  "title": "Vibe Ticket Tracker Ticket Frontmatter",
  "description": "Schema for structured ticket YAML frontmatter in .md files",
  "type": "object",
  "required": ["id", "title", "type", "status", "created", "updated"],
  "additionalProperties": false,
  "properties": {
    "id": {
      "type": "string",
      "description": "Unique ticket identifier in format {prefix}-{NNNNN}",
      "pattern": "^[a-z0-9]+-[0-9]+$"
    },
    "title": {
      "type": "string",
      "description": "Human-readable ticket title",
      "minLength": 1,
      "maxLength": 200
    },
    "type": {
      "type": "string",
      "description": "Ticket type from the configured type options",
      "enum": ["issue", "feat", "bug"]
    },
    "status": {
      "type": "string",
      "description": "Current ticket status",
      "enum": ["open", "closed"]
    },
    "created": {
      "type": "string",
      "format": "date-time",
      "description": "ISO 8601 timestamp of ticket creation"
    },
    "updated": {
      "type": "string",
      "format": "date-time",
      "description": "ISO 8601 timestamp of last ticket update"
    }
  },
  "examples": [
    {
      "id": "issue-00001",
      "title": "Add login page with OIDC auth",
      "type": "issue",
      "status": "open",
      "created": "2025-01-15T10:30:00Z",
      "updated": "2025-01-15T10:30:00Z"
    }
  ]
}
```

### 5.2 Schema Design Rationale

| Constraint | Reason |
|---|---|
| `additionalProperties: false` | Prevents unknown fields from being silently stored; keeps the schema strict and self-documenting |
| `id` pattern `^[a-z0-9]+-[0-9]+$` | Enforces `{prefix}-{number}` format (e.g., `issue-00001`) |
| `title` max 200 chars | Prevents excessively long titles; keeps filenames manageable |
| `type` enum from config | Must match one of the configured `VIBE_TRACKER_TICKET_TYPE_OPTIONS` values (`issue`, `feat`, `bug`) |
| `status` enum `["open", "closed"]` | Minimal lifecycle — only two states allowed |
| `created` / `updated` date-time | ISO 8601 format for consistent parsing and sorting |

### 5.3 Dynamic Validation

At runtime, the `type` enum values are derived from the `vibe-ticket-tracker.json` config (`VIBE_TRACKER_TICKET_TYPE_OPTIONS`). The schema file above provides the static structure; the actual validation loads the type options from config.

If `VIBE_TRACKER_TICKET_TYPE_OPTIONS` is `["issue", "feat", "bug"]`, the effective `type` enum is `["issue", "feat", "bug"]`.
